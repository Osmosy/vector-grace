# Реестр требований GRACE: спаны, гейты дрейфа, раннер чекеров

Реализация того, что описано в `references/requirements-registry-rfc-culture.md`
и в разделе **Requirements Registry Gate** навыка `skills/grace/grace-verification`.
Зависимостей нет: Python 3.14, только stdlib.

## Что делает

| Команда | Смысл |
|---|---|
| `parse` | источники → спаны по байтовым смещениям (кэш, пересобирается) |
| `verdict` | вердикт по спану: `question`, `decision`, `background`, `duplicate`, `open` |
| `add-req` | спан → запись `REQ-NNNN` (дословный `raw_text`, без нормализации) |
| `revise` | новая ревизия требования; запись не правится, изменение — ребро `superseded_by` |
| `invariant-add` | инвариант с обязательным списком переходов и sha256 предиката |
| `measure` | замер предиката на посаженных дефектах: пропуск и ложное отклонение |
| `evidence` | запись доказательства: `req_hash`, `code_hash`, версия чекера, `defeater` |
| `coverage` | гейт покрытия спанов |
| `drift` | гейт дрейфа: устаревшее доказательство, недоказанное требование, сирота |
| `replay` | перезапуск чекеров по `(req_id, code_hash)` и сверка с записью |
| `status` | сводка |

Коды выхода: `0` чисто, `1` блокирующие находки, `2` плохой вход,
`3` запускать нельзя (подменён предикат, инвариант без переходов).

## Раскладка проекта

```
docs/requirements-registry.jsonl   требования (append-only, источник истины)
docs/registry/sources.json         объявленные источники: файл, канал, спикер, дата
docs/registry/spans.jsonl          спаны (кэш, пересобирается из источников)
docs/registry/verdicts.jsonl       вердикты по спанам, с provenance
docs/registry/invariants.jsonl     инварианты: переходы, предикат, версия, замер
docs/registry/evidence.jsonl       записи доказательств (append-only)
```

## Правила, которые проверяются механически

- **Спан — диапазон байт, а не суждение.** `raw_text` требования равен байтам спана;
  `req_hash = sha256(raw_text)`. Пересказ не проходит: длина `span` не совпадёт
  с длиной текста, хэш требования — с хэшем `raw_text`.
- **Идентификатор спана привязан к содержимому**, а не к позиции: правка соседнего
  абзаца не обнуляет вердикт, правка самого спана — обнуляет, и это видно как
  непокрытый спан, а не как тихая потеря.
- **Каждый спан имеет вердикт.** Нет вердикта — блок. Модальный спан (`must`,
  `не менее N`, `должен`) в статусе `background` — блок, а не суждение на глаз.
- **`open` без владельца и срока не создаётся.** «Не разобрал» — законный вердикт,
  но только с дословной цитатой из спана; пересказ цитатой не считается.
- **Три класса дрейфа** — джойны: `evidence.req_hash` ≠ текущий хэш → устаревшее
  доказательство; требование в силе без проходящего доказательства → недоказанное;
  ссылка на `REQ-…` в коде, тестах или реестре без живого требования → сирота.
- **`defeater` обязателен**: без наблюдения, которое опровергнет запись, она декоративна.
- **Приёмка — перезапуск, а не чтение лога.** `replay` сверяет sha256 предиката с
  записанной версией и запускает его; расхождение версии — отказ с кодом 3.

## Запуск

```bash
python3 registry/grace.py --root <проект> parse
python3 registry/grace.py --root <проект> coverage --json
python3 registry/grace.py --root <проект> drift --json
python3 registry/grace.py --root <проект> replay
python3 registry/grace.py --root <проект> status
```

Рабочий пример со всеми тремя чистыми гейтами: `registry/examples/mini/`
(`bash run.sh`). Если убрать `range(attempts)` из `src/upload.py`, `replay`
обязан покраснеть — проверка не пустая.

Тесты: `cd registry && python3 -m unittest discover -s tests -t .`

## Замер предиката (`measure`)

Предикат — классификатор, у него две ошибки: пропуск дефекта и отклонение
корректного кода. Второе в автоматическом конвейере дороже: агент начнёт
«чинить» правильный код. Поэтому до приёмки нужны числа, а не впечатление.

```bash
python3 registry/grace.py --root <проект> measure --inv INV-0001 --by <кто>
python3 registry/grace.py --root <проект> measure --inv INV-0001 \
    --predicate checkers/candidate.py --json      # кандидат, в реестр не пишется
```

Набор дефектов — `bench/bench.json`: файл подмены, эталон чистого варианта и
список дефектов с классом. Замер зарегистрированного предиката пишется в
`docs/registry/measurements.jsonl`, и `evidence` подхватывает его в поля
`measured` — доказательство несёт ту версию предиката, которая реально измерена.
Кандидат в реестр не попадает: он войдёт в инвариант только новой версией чекера
с новым `sha256`, иначе `replay` обязан отказать.

Результат на демо-модуле (`registry/examples/mini/bench/RESULTS.md`): строковый
предикат ловит 1 дефект из 5 (пропуск 0.8), AST-вариант — 5 из 5 при нулевом
ложном отклонении на чистом коде; AST-вариант писался по этому же набору, поэтому
5/5 — оценка сверху, а не измерение обобщения.

## Чего это не даёт

- **Полноты против корпуса.** Гейт доказывает, что у каждого спана есть вердикт,
  а не что в тексте есть все нужные требования. Атомизация + независимая
  переэкстракция + подписанная базовая линия — процесс, а не код.
- **Требований, которых нет в тексте.** Они видны только как `open` с владельцем
  и сроком; их число на базовой линии — метрика риска, а не ноль.
- **Качества самих требований** — это ISO/IEC/IEEE 29148, отдельная ось.
- **Обобщения замера.** `measure` даёт числа на конкретном наборе дефектов:
  набор, по которому правили предикат, перестаёт быть отложенным, а пять классов
  дефектов — не все классы. Ноль в полях замера означает утверждение о качестве,
  поэтому до прогона там `null`.
