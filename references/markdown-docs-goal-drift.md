# Почему отдельная Markdown-документация вызывает дрейф целей агента (а Doxygen — нет)

> Наблюдение автора GRACE (Владимир Иванов) + рефлексия DeepSeek. Записано 2026-07-04.
> Контекст: кастомизация ComfyUI (~2 млн строк). Для фикса багов и первого нового модуля
> Markdown работал. Но в другой сессии на АДМИНИСТРАТИВНОЕ действие агент ложно вывел, что
> надо продолжать в контексте РАЗРАБОТКИ проекта → дрейф.

## Корневая причина
- **Встроенная в код документация (Doxygen/JavaDoc)** описывает ЦЕЛЬ модуля/класса/метода —
  «что делает этот кусок кода». Не создаёт нарратив. Дрейф целей вызвать не может.
- **Markdown-документация (AGENTS.md и т.п.)**, как учат писать агентов, — это «сторителлинг»:
  описывает сценарии/архитектуру/продукт. Для ИИ достоверна гипотеза, что ЭТОТ сценарий и есть
  ЦЕЛЬ. При нескольких MD-файлах агент может счесть один из них «main use case».
- Усиление: агенты, когда пишут MD по сессии, считают, что в сессии и БЫЛ main use case (раз
  они им занимались). Для 100% автономных агентов особо коварно — случайно цепляют деталь
  сценария модуля и пришивают к текущей задаче.

## Рефлексия DeepSeek (точный механизм)
```
AGENTS.md → "ClearRefine SPA + FastAPI + ComfyUI pipeline"
         ↓
Фрейм сессии: "мы дорабатываем ClearRefine, ComfyUI — часть пайплайна"
         ↓
Все решения фильтруются через "как это влияет на проект"
         ↓
Проектные артефакты (доку в корень проекта, объяснения в терминах архитектуры)
         ↓
Пользователь: "я просто хочу настроить ComfyUI"
```
Проявления дрейфа: сохранил доку в корень проекта (не по просьбе); объяснял «как вписывается в
архитектуру» вместо «что и где лежит»; чинил EPERM/ONNX как «чтобы работало в проекте», а не
«потому что пользователь хочет». Doxygen так не делает — он про конкретный API, а не нарратив.
Нужно было в НАЧАЛЕ спросить: «эта настройка ComfyUI — для проекта ClearRefine или отдельно?».
Классическая ошибка over-reliance на контекст без валидации.

## Практический вывод
1. Не принимай нарратив из AGENTS.md/README/проектных MD за ЦЕЛЬ сессии. Это фон, не задача.
2. В начале сессии валидируй фрейм у пользователя, если ambient-нарратив ≠ явная просьба:
   «это в рамках проекта X или отдельная задача?».
3. Goal бери ВЕРБАТИМ из запроса пользователя, а не выводи из документации.
4. Предпочитай встроенную (code-level) документацию нарративной, где важно избежать дрейфа.
5. Осторожно с авто-генерацией session-MD: агент склонен канонизировать сессию как main use case.

Ложится на OBSERVE-фазу навыка the-algorithm (Goal-литерал + «могу ли я ошибаться в том, что
значит done?») и на hindsight-memory-practice.
