# Anthropic: конвейер code review, когда 90 % кода пишут агенты

**Дата записи:** 2026-10-17
**Источник (промо, присланное пользователем):** пересказ практики команды Claude Code — «более 90 % кода пишут ИИ-агенты», рост принятых PR вдвое с июня по сентябрь, доля откатов ниже на 40 %, многоагентное ревью на PR, риск-классы для человеческого одобрения, очередь слияния, флаги и откаты.
**Первоисточники (прочитаны):**
- `code.claude.com/docs/en/code-review` — документация продукта Code Review (первоисточник по механике и ограничениям);
- `claude.com/resources/articles/code-review` — статья Anthropic «Bringing Code Review to Claude Code» (09.03.2026) с числами;
- `claude.com/resources/articles/code-review-is-now-generally-available` (15.10.2026) — GA, уровни ревью, скорость.
**Вторичный уровень (первоисточник недоступен):** практика команды Claude Code внутри Anthropic (90 % своего кода, рост PR, откаты, правила раундов) известна по посту команды, который читается в пересказах — HN, dev.to, O'Reilly Radar (запись разговора Cat Wu с Addy Osmani), отраслевые брифинги. Числа оттуда помечены ниже как вторичные.

## Что подтверждается документацией продукта (первоисточник)

**Механика ревью — четыре стадии:**
1. **Find** — несколько агентов параллельно читают диф и окружающий код;
2. **Verify** — отдельная стадия проверяет кандидатов в находки по коду и **отбрасывает ложные срабатывания**;
3. **Rank** — найденное дедуплицируется и ранжируется по серьёзности;
4. **Post** — инлайн-комментарии по строкам + сводка + check run «Claude Code Review».

- По умолчанию фокус — **корректность** (баги, ломающие продакшн), а не форматирование и не отсутствие тестов; поведение настраивается файлами **REVIEW.md** и **CLAUDE.md** в репозитории.
- **Ревью не одобряет и не блокирует PR** («A review never approves or blocks the pull request»), а check run **не завершается статусом failure**. Блокировку по находкам нужно настраивать в своём CI — промо говорит это верно.
- `REVIEW.md` берётся **из базовой ветки и никогда из изменений самого PR** — прямое следствие: PR не может переписать правила собственного ревью.
- Доступ: только чтение репозитория, коммиты не пушатся; ревью идёт на инфраструктуре Anthropic (self-hosted не поддерживается).
- **«Ревью работает чтением дифа и окружающего кода, без сборки и запуска вашего кода»** — ключевое ограничение продукта.
- Уровни: Quick / Standard (по умолчанию) / Deep, выбираются на организацию и на отдельный репозиторий; модели фиксированы, выбора нет.
- Доступность: планы Team и Enterprise, GitHub (включая GHES и GHEC с data residency); недоступно при Zero Data Retention, HIPAA-конфигурации и CMEK.

## Что известно только по вторичным пересказам (пост команды)

Помечаю отдельно, потому что в промо эти числа поданы как внутренние данные без оговорок:

- «Claude пишет около **90 %** собственного кода Claude Code» (формулировка команды) — при этом в пересказе разговора Cat Wu на O'Reilly AI Codecon та же цифра звучит шире: 90 % **всей кодовой базы Anthropic**. Область действия в двух версиях разная, и это стоит держать в голове: «90 % своего продукта» и «90 % всей компании» — не одно и то же.
- Принятые PR в Claude Code **больше чем удвоились** с июня по сентябрь, доля откатов упала **более чем на 40 %**.
- Изменений в монорепозитории Anthropic: ~**2 500** в день в мае → **более 30 000** в сентябре.
- Цель: большинство PR в репозиториях Claude Code сливаются при **не более чем одном человеке в контуре** (им может быть автор), без роста откатов и инцидентов. Метрики человеческого времени: число человеческих одобрений на PR (медиана и 95-й процентиль), человеческие комментарии, время ожидания человеком. Страж — частота откатов и инцидентов.
- Правила против пинг-понга агентов (один CLI-PR ушёл в **50+ раундов** за ночь; **59 %** повторных находок приходили из первого прохода, а не из новых багов):
  после **трёх раундов** ревьюер обязан попросить автора пересмотреть подход; после первых проходов проверяется **только новая разница**; класс ошибки помечается, чтобы автор исправил все вхождения сразу; уже опубликованные замечания не повторяются.
- Метрики после этих правок: PR, проходящие за один цикл ревью — 65 % → **78 %**; PR, которым нужно 5+ раундов — 8.9 % → **1.5 %**; среднее число ревью до прохода — 2.08 → **1.32**.
- Очередь слияния перепроверяет всё против **актуального main**; новое поведение выпускается под флагами сначала на сотрудников, канал `stable` отстаёт от `latest`; еженедельное дежурство; разбор каждого инцидента отвечает на вопрос **«какой слой должен был это поймать?»**, а инциденты и откаты превращаются в ежедневные тесты проверяющего агента.

## Где промо сглаживает факты

- **«Агент запускает тесты, сборку или проверку интерфейса и предъявляет результат»** — это внутренняя практика команды Claude Code (перед открытием PR), а **не** поведение продукта Code Review: по документации ревью **не собирает и не запускает код**, а его check run никогда не падает. Если ждать от продукта прогонов — ожидание не сбудется.
- **«Доля откатов снизилась более чем на 40 %»** подано как следствие ревью; по вторичным пересказам это цифра за период июнь → сентябрь по всему потоку изменений команды, а не эффект одного инструмента (там же флаги, очередь слияния, откат без деплоя и разборы инцидентов).
- **«Блокировка агента привязана к коммиту»** и «одобрение агента не заменяет человеческое» — в промо звучит как свойство системы; в документации подтверждается только то, что продукт не одобряет и не блокирует PR вообще. Остальное — внутренние надстройки команды, их надо строить самому.

## Что из этого стоит перенести (и куда именно)

1. **Параллельный поиск + отдельная стадия проверки находок.** Это ровно то, что в GRACE сформулировано как недопустимость самооценки: находки обязана подтверждать независимая стадия, а не тот, кто их нашёл (`grace-tests-as-logs-and-evidence.md`, навык `grace-diagnostics`).
2. **Правила ревью читаются из базовой ветки и никогда из изменений PR.** Готовое решение проблемы «правки PR переписывают критерии собственного приёма». В наших терминах: `REVIEW.md`/AGENTS.md и `criteria.json` берутся из main, а не из ветки PR.
3. **Риск-классы для человеческого одобрения:** низкий риск — без человека, средний — один, высокий — два; первый классификатор назначает уровень, второй проверяет необходимость дополнительного человека; послабления только для доверенных авторов; чувствительные пути и файлы CI требуют человека; одобрение привязано к коммиту, новые изменения требуют повторного согласования. Это готовая схема для нашего гейта приёмки: доля пунктов спеки с доказательством + уровень риска → сколько человеческих глаз нужно.
4. **Очередь слияния, перепроверяющая проверки против актуального main.** Прямой аналог «приёмка привязана к коммиту», но на уровне всей очереди: то, что было зелёным на старом main, перепроверяется на новом.
5. **Инцидент → ежедневный тест проверяющего агента.** Превращение отказов и инцидентов в регрессии для самого ревьюера (а не только для кода) — этого у нас пока нет; сильный ход против «зелёного ревьюера».
6. **Метрики ревью как отдельный прибор:** человеческие одобрения на PR (медиана и p95), человеческие комментарии, время ожидания человеком, доля ложных находок, число раундов. В промо из этого оставлены только PR и откаты.
7. **Анти-пинг-понг для агентских ревью:** три раунда → пересмотр подхода; после первых проходов — только новая разница; исправлять класс ошибок; не повторять опубликованное. Это дешёвая защита от оверхеда, который иначе съедает всю экономию агентского ревью.
8. **Стоимость как параметр архитектуры:** $15–25 за PR — то есть глубокое многоагентное ревью уместно на PR и релизе, а не на каждый коммит (совпадает с раскладкой в `agentic-e2e-vs-scripted-tests.md`).
9. **Check run без failure — не ошибка продукта, а разделение ответственности.** Ровно то, чего не хватает тем, кто ждёт «зелёного» как разрешения: гейт должен быть своим, а ревью — источником находок.

## Границы применимости

- Продукт доступен только на Team и Enterprise, только GitHub, без Zero Data Retention, HIPAA и CMEK — то есть как готовый инструмент он закрыт для части организаций.
- Ревью не запускает код и не проверяет поведение: для «доказательного» контура нужны свои прогоны, телеметрия и критерии в журнале (`diagnostics-over-tests-dirty-data.md`).
- Числа 90 %/2×/−40 % относятся к потоку изменений внутри Anthropic с их культурой измерений, флагами и дежурствами; переносить их на другой проект как ожидаемый эффект нельзя.
