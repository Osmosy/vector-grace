# Поиск для ИИ-агентов: нет победителя — есть маршрут

Source: Сергей Пименов, pimenov.ai — «Как я тестировал поиск для ИИ-агентов и не нашёл одного победителя» (https://pimenov.ai/articles/test-poiska-dlya-ai-agentov/), август 2026

## Эксперимент

24 одинаковых запроса (8 тем × 3 намерения: свежесть / первоисточник /
решение) через три контура: обычный веб-поиск, Keenable, Firecrawl.
Бесплатные лимиты, $0 расходов. План заморожен до запуска; ограничения
задокументированы (Firecrawl без query_time — «приблизительно сопоставимо»).

Единоличные победы: веб-поиск 14, Keenable 3, Firecrawl 2, ничьих 5.

## Главная мысль

«Поиск» для агента — это минимум четыре разные работы, и один инструмент не
закрывает все:

1. широкий поиск — заметить релевантное среди шума;
2. точечный поиск — вернуть страницу по точному намерению;
3. извлечение — получить из URL полный чистый текст;
4. редакторская проверка — связать утверждение с источником.

Требование «найти один лучший поисковик» исчезает, когда роли разделены.
Появляется маршрут: найти → выбрать источник → получить текст → проверить
утверждение → принять решение.

## Роли инструментов (пилот)

| Слой | Сильная сторона | Ограничение |
|------|----------------|-------------|
| Обычный веб-поиск | широта: Reddit, HN, русскоязычное, независимые исследования; конфликтующие точки зрения на решающих запросах | 4/48 страниц не открылись → разведка, не загрузчик |
| Keenable | второй проход по первоисточникам: документация, тарифы, changelog, срез на дату; 48/48 загрузок | слаб на широких, социальных, локальных запросах; supplement_not_replace |
| Firecrawl | извлечение полного HTML после выбора URL (длинные страницы NIST, PMC, Apple) | не поисковик; на свежем поиске шум (LinkedIn, SEO) |

## Инцидент с кредитами (главный практический урок)

Один X-запрос через Firecrawl proxy=basic списал 30 кредитов вместо
документированных 1–5, лимит 96 пробит → 113. Защитный контур узнал
постфактум. Вывод автора: пока провайдер не даёт предрасчёт стоимости —
запрещённые домены (X, Reddit), потолок кредита на вызов, стоп на следующий
вызов, проверка метаданных после КАЖДОГО вызова. Кредиты потраченные не
вернуть — можно только не продолжать каскад.

## Контур, который он оставил

Веб-поиск (разведка) → Keenable (первоисточники, второй проход) →
редакторский отбор URL → Firecrawl (только выбранные страницы) → реестр
утверждений («утверждение → источник → дата → ограничение») → человек
принимает решение о публикации.

## Правила из пилота

План замораживается до запуска; намерения разделяются; вызовы и полезные
источники считаются отдельно (успешный ответ ≠ редакционная ценность);
тест на реальных темах; поиск ≠ извлечение; стоп на следующий вызов;
человек-гейт за вывод.

## Оценка метода

Сильно: замороженный план, скрытые ограничения не скрыты, отрицательный
результат по расходам задокументирован точно и с оговорками. Главная мысль —
архитектура маршрута вместо рейтинга инструментов — недооценена и верна.

Слабо: N=24, один оценщик (автор статьи), Keenable без ссылки на описание,
кредитный вывод Firecrawl построен на одном инциденте (сам оговаривает).

## Связь с нашим toolchain

Та же трёхслойная архитектура уже есть в Hermes: web_search (разведка) →
web_extract (извлечение) → blocked-page-recovery (403/WAF). Инцидент с
кредитами — аргумент за least privilege при делегировании агенту платных
инструментов: явные лимиты, стоп-линия, доменные запреты (ср.
delegation-gate-checklist).

## Практический вывод

Надёжный ИИ-материал начинается не с выбора сервиса, а с маршрута:
разделить роли поиска, извлечения и проверки — потом выбирать инструменты.
