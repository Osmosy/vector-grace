# Indra OCR: 1M параметров, 49 страниц/с на 32 ядрах — и что он даёт на наших слайдах

**Дата записи:** 2026-10-17
**Источник (промо, присланное пользователем):** «Indra: OCR-модель всего на 1M параметров, которая рвёт PaddleOCR и Tesseract по скорости» — 49 страниц/с на CPU, в 11 раз быстрее PaddleOCR и в 17 раз быстрее Tesseract, качество 41.3 против 35.8 и 19.3 на OmniParseBench, полная разметка страницы и bounding box по строкам.
**Первоисточники (прочитаны целиком):** карточка модели `huggingface.co/datalab-to/indra-ocr`, блог `datalab.to/blog/indra-ocr` (Vik Paruchuri), репозиторий `github.com/datalab-to/indra`. Бенчмарк — **собственный** OmniParseBench того же автора; независимых прогонов нет.

## Что подтверждается цифрами первоисточника

| Утверждение промо | Первоисточник | Комментарий |
| --- | --- | --- |
| модель на 1M параметров | 1.24M параметров (карточка), «about 1M» у распознавателя `rec.onnx` | подтверждается |
| 49 страниц/с на CPU | 49.4 страницы/с **на 32 ядрах** (AMD EPYC, без GPU) | подтверждается, но промо опускает «32 ядра» |
| в 11 раз быстрее PaddleOCR | 11.5× на 32 ядрах (49.4 против 4.28 у PP-OCRv6 small через RapidOCR) | подтверждается для этого режима |
| в 17 раз быстрее Tesseract | 16.9× на 32 ядрах (Tesseract 5 — 2.92 стр/с) | подтверждается |
| качество 41.3 против 35.8 и 19.3 | OmniParseBench text: Indra 41.3, PP-OCR text models 35.8, Tesseract 5 19.3 | подтверждается (их бенчмарк) |
| разметка и боксы | бокс на каждую строку и каждый layout-блок, метки (заголовки, списки, таблицы, подписи, сноски, колонтитулы), порядок чтения, markdown/JSON | подтверждается |
| локально без GPU | ONNX Runtime, без PyTorch, ~18 МБ моделей, `pip install indra-ocr`, Python ≥ 3.10, Linux x86_64/aarch64 | подтверждается |

Дополнительно из первоисточника: латентность ~230 мс на страницу на 4 vCPU; профиль по ядрам — 7.3 / 14.2 / 27.2 / 49.4 стр/с на 4 / 8 / 16 / 32 ядрах; страницы с текстовым слоем PDF читаются за 130 мс (медиана) против 304 мс для страниц, которым нужен OCR; полный счёт 62.1 при таблицах 56.4 и разметке 88.6; режим `--math` поднимает текст до 57.5, но **снижает таблицы** 56.4 → 54.8 (часть чисел в ячейках читается как математика).

## Где промо молчит (важное)

- **Лицензия весов — модифицированная OpenRAIL-M**: бесплатно для исследований, личного использования и стартапов с финансированием/выручкой до $20 млн, и **весов нельзя использовать в конкуренции с их API**. Код — Apache-2.0. В промо про лицензию нет ни слова, а для коммерческого продукта это ограничение существенно.
- **«Рвёт PaddleOCR и Tesseract» — это их собственный бенчмарк** (OmniParseBench, 16 288 тестов на 2 937 страницах) и их harness; Tesseract шёл с латинской моделью по умолчанию. Независимых замеров на дату разбора нет.
- **Проект совсем свежий**: репозиторий создан 13.10.2026, 16 звёзд, 1 релиз, 1 053 загрузки модели за месяц. Это не «проверенный временем» инструмент.
- **Ограничения заявлены самими авторами**: сложные таблицы (многоуровневые заголовки, объединённые ячейки, отсутствие линий сетки) теряют структуру; рукописный текст ~8 %; на сканах и картинках OCR только латиница, **кириллица**, греческий, деванагари, бенгальский и китайский — арабский, иврит, тайский, японские каны, корейский читаются только из текстового слоя цифрового PDF; вертикальный текст не поддерживается; математика — обычным текстом, если не включить `--math`.

## Мой прогон на наших данных (17.10.2026)

Поставил локально: `uv venv --python 3.13` + `uv pip install indra-ocr` → venv 305 МБ (системный Python 3.14 не годится: нет `ensurepip`/`python3.14-venv`). Модели скачались с Hugging Face при первом запуске (~18 МБ, пара секунд).

**Слайд 154** (плотная русская таблица + диаграмма — тот самый слайд, на котором раньше сравнивали качество OCR):

- время: **404 мс** на страницу (OCR-режим, один воркер), 3.7 с с учётом первого скачивания моделей;
- из 18 эталонных чисел **все присутствуют**, но **четыре с дефектами формата**: `1 062` → прочитано как `062`, `1 800` → `800` (потеряна ведущая единица в числах с пробелом-разделителем разрядов), `−10 %` → `10 %`, `−16 %` → `16 %` (потерян минус);
- строгое совпадение токенов — **16 из 18**; оба промаха относятся к классу «формат числа», а не «выдуманное число»;
- лишних придуманных чисел не видно: все прочие токены (`160`, `150`, `200`, `667`, `100`, `130`, `867`, `1,6 %`, `2025`) действительно есть на слайде — сверил глазами по изображению.

**Слайд 194** (мелкий текст на карточках упаковки, ранее признан трудным для чтения): **147 символов** и мусор («СБИН», «МИРАТОР», «Alimentari», «he», «ni», «e») — непригодно. Это ровно тот случай, о котором предупреждают авторы: деградированные сканы и мелкий текст — не его задача.

## Выводы

1. **Для чистых печатных страниц и цифровых PDF — да, брать.** 404 мс на страницу на нашей машине, полный набор чисел на плотной русской таблице, markdown/JSON с боксами и порядком чтения. Как массовый локальный проход (классификация, сегментация, первичное извлечение, разметка боксами, «где вообще есть текст») это на порядок дешевле облака.
2. **Для номера критичных извлечений — нет, не замена облачным vision-моделям.** Их ~98 % чисел на растровых таблицах пока выше: Indra даёт значения, но портит формат (разряды, знак), а на слайдах с мелким текстом (194, а по опыту и 67/176) выдаёт мусор. Если ставить в конвейер — обязательно с пост-нормализацией чисел (пробел-разделитель разрядов, минус) и с обязательной сверкой на «злых» слайдах.
3. **Класс ошибки предсказуем и проверяем.** Дефекты форматные, а не выдуманные значения, — значит ловятся машинной проверкой (нормализация + сверка с эталоном), чего не скажешь о галлюцинациях vision-моделей. Для EBT-контура это плюс: ошибку можно поймать критерием в журнале.
4. **Лицензия — узкое место для продукта.** Веса OpenRAIL-M: нельзя использовать там, где это конкурирует с их API, и бесплатность ограничена $20 млн выручки/финансирования. Для внутренних пайплайнов и исследований — ок, для коммерческого продукта — читать LICENSE.
5. **Ниша, где он сильнее всего:** цифровые PDF — чтение текстового слоя в любом скрипте (включая арабский, иврит, японский) плюс OCR только для того, что пропущено; и 130 мс на страницу — это дешевле любой альтернативы.

**Как проверить у себя (повтор):** `uv venv --python 3.13 ~/.venvs/indra && uv pip install --python ~/.venvs/indra/bin/python indra-ocr`, затем `~/.venvs/indra/bin/indra-ocr <файл> --format json --timings`; сверять числа нормализованно (убрать пробелы-разделители и учесть знак), а не подстрокой — иначе дефект `062` вместо `1062` не видно.

## Решение (17.10.2026)

- **В общий конвейер не ставим.** Применяем только там, где качество сканирования гарантировано: чистая печать, цифровые PDF, крупный текст. На деградированных сканах, мелком тексте и растровых таблицах с числами (типа слайдов 194, 67, 176) — не используем: там остаются облачные vision-модели с их ~98 % по числам.
- Разбор в репозиторий **не пушим** (локальный коммит `13a1bac`), в README строка добавлена.
- Окружение оставлено на месте (`~/.venvs/indra`, 305 МБ + ~18 МБ моделей) — на случай разовых задач по чистым документам и как быстрый детектор «где есть текст».
