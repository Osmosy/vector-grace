# PreciseCoder: unit-тест как единственная награда в GRPO деградирует модель

**Дата записи:** 2026-10-17
**Источник (эссе пользователя):** тезис, что unit-тесты «в лоб» на GRPO-обучении дают деградацию: over-editing (рост размера правок) и галлюцинация багов в корректном коде (no-op падает с 30.8 % до 20.5 %); решение авторов — добавить F1 к эталонному diff; вывод эссе — датасет «задача — код — тесты» без истории правок нерабочий; главный инсайт — оценка кодирующей модели только по тестам ведёт к многогранному развалу качества обучения.
**Первоисточник:** `arXiv:2610.18755` — **PreciseCoder: Faithful and Generalizable Debugging Beyond Unit-Test Rewards** (Yunkai Zhan, Miaosen Chai, Shangshang Wang, Jike Zhong, Yuqing Yang, Deqing Fu, Serina Chang, Wang Bill Zhu; 2026-10-13). Разбор по полному тексту (HTML-версия), числа сверены с таблицами статьи.

## Что подтверждается дословно

**1. Over-editing — обучение действительно учит править больше.**
- Средний размер правки на обучающем наборе растёт с **3.94 до 8.28 строк** по ходу RL.
- На PDB Test (Qwen3.5-4B): GRPO тратит **13.8 строк** на правку против **3.0** у PreciseCoder при практически равном pass rate (55.1 % против 55.3 %); 9B — 11.9 против 3.0; 27B — 7.9 против 2.6.
- На SWE-Bench Verified (перерасход строк относительно gold-патча на решённых задачах): **GRPO +58 %**, EA-GRPO +37 %, PreciseCoder-9B +29 %.
- Масштаб явления у frontier-моделей (их собственная справка из статьи): GPT-5.1-Codex проходит 76 % задач PDB, но **лишь 40 % правок необходимы**; смердженные PR от кодинг-агентов нуждаются в ручной правке человека в **45 %** случаев (Watanabe et al., 2025).

**2. Галлюцинация багов в корректном коде — ключевая находка, числа совпадают с эссе.**
- На валидационном наборе из **200 безошибочных программ** no-op rate падает с **30.8 %** в начале обучения до **20.5 %** (среднее по трём последним оценкам) — модель обучалась только на багованном коде, «правильный» код ей в обучении не показывали, но эффект на нём измерим.
- В основной таблице (Qwen3.5-4B, набор GT Debug из 1 512 корректных программ): no-op — база 30.6 % → **GRPO 19.3 %** → PreciseCoder **48.0 %**; damage (доля корректных программ, сломанных правкой, по тестам) — GRPO 17.8 % → PreciseCoder 13.5 %. На 27B: GRPO 26.9 % no-op → PreciseCoder 45.8 %.
- Pass rate при этом **не падает**: 4B 55.1 → 55.3, 9B 63.9 → 62.5, 27B 76.3 → 79.3. То есть «деградация» — это не про проход тестов, а про достоверность: падает precision (доля необходимых правок) 4B 30.0 → 64.9, 9B 41.7 → 67.7, 27B 43.2 → 79.2, при росте recall.

**3. Решение — награда-смесь с F1 по эталонному diff.**
- Формула: **r_λ = (1 − λ)·unit + λ·F1**, где `unit` — сигнал прохождения юнит-тестов, а **F1 считается по отредактированным строкам относительно референсного (gold) патча** (precision — доля необходимых правок среди сделанных). В статье λ = 1/3 (допустимый диапазон: λ < 2/(2+√(2G)), при G = 6 это λ < 0.37).
- Отдельный методический нюанс, важный для инженеров: стандартная групповая стандартизация GRPO на сумме терминов **коллапсирует** (в группах, где `unit` константен, остаётся только F1), поэтому авторы используют **GDPO** — по-терминную стандартизацию внутри группы до смешивания. Если добавлять к тестовой награде второй критерий, нормировать надо раздельно.
- Генерализация: обучение только на **однострочных** багах (5 274 задачи PDB-Single-Full, синтезированные на задачах BigCodeBench/LiveCodeBench; тест — 1 205 отложенных задач) переносится на репозиторный ремонт: SWE-Bench Verified 9B — **32.7 %** решённых задач (база 25.9, unit-test-only GRPO 28.1, EA-GRPO 27.1), 27B — **70.8 %** (база 67.9, GRPO 69.5). Если gold-патч уже применён, PreciseCoder-27B ломает 8.9 % репозиториев против 11.0 % у базы и **13.1 % у GRPO**.
- Weak-to-strong: один только **reasoning-трейс** 9B-донора поднимает precision правок у frontier-моделей (GPT-5.6 Sol, Qwen3.8-Max) на **4.6–12.4 п.п. без обучения**. Лингвистический разбор трейсов: работает не ответ, а дисциплина рассуждения — назвать багованные строки поимённо и взвесить каждую правку.

## Что в эссе перегибает (или требует уточнения)

- **«Деградация модели»** — точнее: деградация *достоверности* при сохранении pass rate. По тестам GRPO не проседает; проседают precision (30–43 % необходимых правок), объём правок (×3–4) и сохранность корректного кода (damage 11–18 %).
- **Авторы не отказываются от unit-теста.** Он остаётся первым слагаемым награды; лечится именно режим «unit-test-only», а не «unit-тест».
- **«F1 как минимальный дополнительный критерий»** — да, ровно так, и вывод эссе про датасет верен: F1 считается против эталонного diff, поэтому набор «задача + код + тесты» **без истории правок** для этого метода нерабочий (в статье обучение идёт на корпусе с синтезированными gold-патчами).
- **«Альтернатива — включение тестов в более комплексные оценки критиков»** — согласуется с вендорской практикой (см. `rl-training-semantic-signals.md`: MiMo-V2.6 GRS прямо складывает рубричные оценки критика с test rewards, GLM-5 держит rule-based rewards одним из трёх сигналов).
- **Трение с эссе про RL-обучение:** эта статья называет «единый unit-test-outcome как награду» **доминирующим рецептом лабораторий** («A common post-training recipe reported by leading AI labs is reinforcement learning with verifiable rewards, using unit-test outcomes as the sole reward signal»). То есть тесты из контура не выброшены — их лечат добавками (рубрики, GRM, F1), и это ровно то, что описано у MiMo и GLM-5.

## Практические выводы для пайплайнов агентов

1. **Мерить не «прошло/не прошло», а нужность правки.** Минимальный набор метрик для оценки агента-ремонтника: precision и recall правок против ожидаемого изменения, размер патча, no-op и damage на корректном коде. Pass rate этого не показывает (пример: 76 % pass при 40 % необходимых строк).
2. **«Ничего не менять» — это положительный результат.** Способность сказать «код корректен» надо и обучать, и оценивать: без этого агент, натренированный только на багах, начинает ломать рабочий код (no-op 30.6 % → 19.3 %).
3. **История правок — обязательный артефакт проекта.** Без референсных изменений (или gold-патчей) нельзя ни обучить, ни оценить достоверность ремонта; у проекта должна быть память о том, как выглядит «правильная» правка.
4. **Дисциплина трейса переносима бесплатно.** Требование «назови конкретные багованные строки и обоснуй каждую правку» улучшает precision даже без обучения (эффект донора 4.6–12.4 п.п. на frontier-моделях) — это дешёвая промпт-практика для агента.
5. **Смешивая критерии — нормируй их раздельно.** Практический аналог GDPO в агентном пайплайне: если сигналов несколько (тесты + качество правки + рубрика критика), нельзя складывать их в один скаляр и агрегировать «как получится» — иначе более шумный критерий вытесняет более точный.
6. **Не путать «зелёные тесты» с достоверностью.** Та же ось, что в `ebt-evidence-based-testing.md` и `kun-chen-tdd-and-ground-truth.md`: тест отвечает на вопрос «проходит ли», а не «правильно ли сделано»; второй вопрос требует отдельного сигнала (трассировка к требованию, F1 к референсной правке, рубрика критика).
