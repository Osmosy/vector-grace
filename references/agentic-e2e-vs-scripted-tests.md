# Скриптовые E2E-тесты против агентского тестирования через MCP

**Дата записи:** 2026-10-17
**Источник (позиция автора GRACE, изложена пользователем):** запрограммированные E2E-сценарии — плохая практика: они формируют «safe path», часто нереалистичный, который через UI пользователь 1:1 повторить не может; дальше начинается война с мутационными тестами, тесты распухают больше кода, а качество почти не растёт. Альтернатива — агент, который действует с приложением как пользователь через MCP (иногда с системными вызовами для ускорения); главная ценность — диагностика: развёрнутый отчёт о проблеме со срезом проблемных данных, по которому кодирующая LLM фиксит баг в one shot. Баланс алгоритмического и агентского тестирования обязателен, но полное отсутствие агентского — дефект управления разработкой.
**Опорные файлы:** `grace-tests-as-logs-and-evidence.md`, `ebt-evidence-based-testing.md`, `unit-test-only-reward-degradation.md`, `dsh-field-report-browser-plugin.md`, `ax-tree-rules.md`, `grace-methodology-guide.md`.

## Почему скриптовые E2E плохи (позиция, с обоснованием из смежных разборов)

1. **Safe path ≠ путь пользователя.** Сценарий кодирует тот путь, который автор сценария смог представить; реальный UI-путь (другие порядки действий, состояния, ошибки, тайминги) в него не попадает. Проверка становится самореферентной: она подтверждает не продукт, а представление тестировщика о продукте.
2. **Распухание и мутационная война.** Попытка закрыть дыры мутациями увеличивает объём тестового кода, но не покрытие среды: сигнал растёт медленнее стоимости, тесты становятся дороже сопровождения, чем проверяемый код.
3. **Независимое подтверждение из смежных разборов.** Тот же механизм описан в других разборах: тесты как цель обучения дают рост правок без роста качества (`unit-test-only-reward-degradation.md`), а «зелёные тесты» сами по себе доказательством не являются ни в авиационных стандартах, ни в практике (`ebt-evidence-based-testing.md`, `kun-chen-tdd-and-ground-truth.md`). Скриптовые E2E — частный случай этого: они отвечают на «прошло ли по моему маршруту», а не «работает ли по требованию».

## Чем агентский E2E отличается по существу

| | Скриптовые E2E | Агент через MCP/CLI как пользователь |
| --- | --- | --- |
| Маршрут | заранее закодирован, один | выбирается в прогоне, допускает отклонения |
| Реакция на баг | красный тест, стоп | фиксирует дефект, делает workaround и продолжает проверку |
| Набор проверок | нужен массив мутаций, чтобы закрыть дыры | сам добирает уголки кода по гайду/логам |
| Работа на баговом приложении | невозможна (падает на первом дефекте) | возможна (обход дефекта, чтобы дойти до конца) |
| Результат | pass/fail по сценарию | отчёт: шаги, срез проблемных данных, строки логов, гипотеза, репро |
| Сессии/логины | требуют фикстур и обходов | работает под живой сессией (SSO, 2FA, капча) |

Аналогия автора — «дельтоплан против Шаттла»: снаружи «и то и то летает», по существу это разные классы инструментов. Первый подстраивается под среду, второй требует, чтобы среда подстроилась под него.

## Что подтверждается нашим собственным замером

В разборе `dsh-field-report-browser-plugin.md` (бенчмарк из репозитория плагина, 18.08.2026; парный прогон 6 задач × 5 сидов, одна модель): агентный браузер дал **30/30 успеха при медианной e2e-задержке 5.32 с и 3.4 вызова инструментов против Playwright-бейслайна 30/30, 6.67 с и 4.7 вызовов; отношение времени 1.24 (95 % CI 1.16–1.34) в пользу агентного**. То есть агентный путь не «медленная игрушка»: он уже паритетен по успеху и быстрее по времени, а главное — добавляет работу под реальными логинами, которой у скриптов нет.

Косвенно подтверждается и поведением модели: в нейтральной пробе (17.10.2026, `sft-code-training-and-module-contracts.md`) агент сам собрал контур исполнения — записал код, написал тесты, прогнал, поймал падение, поправил. Раннер он строит без понуканий, а значит «нет агентского тестирования» — это отсутствие управления, а не отсутствие возможности.

## Как распределять роли (баланс, а не дихотомия)

**Алгоритмически, на каждый коммит** — дешёвое, детерминированное, повторяемое:
- evidence-ассерты и инварианты в логе по пунктам спеки (`grace-tests-as-logs-and-evidence.md`);
- проверки контрактов модулей и секций (`sft-code-training-and-module-contracts.md`);
- статические анализаторы, линтеры, мутационный контроль **самих evidence-проверок** (убрали доказательство — тест обязан покраснеть);
- инварианты на критичных участках (состояния, конкурентность, границы).

**Агентно, на PR/релиз и по событию** — дорогое, но дающее диагностику и реальную среду:
- сквозные сценарии через MCP/браузер как пользователь, включая работу под живой сессией;
- приёмка «соответствует ли RFC/change request» по каждому пункту, а не «прошло ли по маршруту»;
- разбор аномалий: агент читает логи, находит срез проблемных данных, формулирует минимальный репро;
- проверка на баговом приложении (обход дефекта, чтобы оценить остальное).

**Метрика приёмки** смещается с «% прохождения» на «доля пунктов спеки, по которым есть доказательство + отчёт агента без открытых обходов».

## Обязательные оговорки и уточнения

1. **Workaround обязан попадать в отчёт как дефект.** Иначе главное преимущество агента (продолжить проверку через обход) превращается в маскировку багов: приложение «принято», а дефект остался неисправленным. В отчёт — отдельное поле «обход применён» с описанием, и он блокирует приёмку до решения.
2. **Агентный E2E не заменяет алгоритмические проверки** — это признаёт и сама позиция; вопрос не «что лучше», а «что на каком шаге конвейера».
3. **Свой класс отказа у агентного теста:** он может «принять» приложение, не проверив требование (дрейф, усталость, подмена критерия). Поэтому evidence-ассерты и независимый критик (`rl-training-semantic-signals.md`) обязательны — иначе агентское тестирование само становится формой самооценки.
4. **Стоимость.** Агентный прогон дороже юнит-теста на порядки; гонять его на каждый коммит не нужно — правильная раскладка: алгоритмическое на коммит, агентское на PR/релиз/по событию.
5. **Измеряемость утверждения «тесты распухают больше кода».** Числа в эссе не приводятся; это проверяемая локально метрика для любого проекта: строк тестового кода / строк кода, число мутаций, пойманных дефектов на 1000 строк тестов. Стоит мерить в своём репозитории, а не спорить.
6. **Гигиена агентного прогона** (из `dsh-field-report-browser-plugin.md`): живая сессия с куками — зона риска (платежи, письма, удаление); управляемую вкладку держать отдельно от личных сессий, пароли/карты не выводить.
7. **Диагностический отчёт — целевой артефакт, а не побочный.** Критерий качества отчёта: по нему кодирующая модель фиксит дефект в one shot, без переписки и без дополнительных вопросов — значит в отчёте обязательны версия кода (хеш коммита), среда, шаги, срез данных, строки логов с корреляционным id, гипотеза и минимальное репро.
