# Навигация ИИ по крупному коду: мифы разработчиков с агентами

> Наблюдение автора GRACE (Владимир Иванов). Записано 2026-07-04.
> Кейс: сложное тестирование сборок workflow для автопайплайна генерации изображений в ComfyUI.
> Приложение ~2 млн строк (500k+ Python, остальное — JSON-конфиги, где значительная часть логики).

Мне сейчас нужно было для одного проекта сделать сложное тестирование разных сборок workflow для автоматического пайплайна генерации изображений. Это делалось в Comfy, поскольку я добавил в него множество нейросетей и компонентов, то общий размер приложения достиг 2 миллионов строк, из них +500 тысяч строк на Python. Остальное — конфигурационные файлы JSON, т.к. значительная часть логики в них.

Поскольку я компоненты ставил свежие, то в них часто были баги или конфликты версий. Поэтому DeepSeek-V4-Flash у меня залезал в исходный код и конфигурации Comfy, чтобы понять в чём проблема или наложить хотфикс. Для этого проекта я сделал DeepSeek-V4-Flash субагента-консультанта из GLM-5.2, чтобы в случае сложных проблем или проверки решений он ходил к GLM советоваться.

Приложение по современным меркам крупное и сложное, но DeepSeek-V4-Flash прекрасно в нём орудовал.

## Наблюдения

1. Тема сложности для ИИ навигации по крупному коду абсолютно раздутая. Не имея никаких MCP или графов, DeepSeek-V4-Flash прекрасно плавал в 2 миллионах строк текста, и это не удивительно. Его Ad Hoc скрипты на Python на такой объём текста вообще-то срабатывают в пределах 1 секунды.

2. Важное наблюдение, что терминальному агенту просто критически важен доступ к исходному коду приложения. Если вы посмотрите тесты DeepSeek-V4-Flash, то заметите, что у него хуже админский Terminal Bench в отличие от теста фиксов SWE Bench. Хотя в человеческих понятиях вроде бы фиксить сложнее, но для ИИ сложнее администрировать black box. Я в бизнес-агентах всегда им даю доступ к исходному коду на чтение, чтобы они понимали реакцию Tools в случае проблем.

3. Ранее я описывал пример приложения, где ИИ-агенты писали его с нуля и делали документацию в отдельных Markdown-файлах и очень быстро запутались в них с деградацией. Однако вот для правок 2 миллионов строк legacy кода/конфигов прекрасно работает MD-документация. Почему? Просто «ломать не строить»: задача просто пофиксить баг — задача для ИИ не сложная. Вообще-то приложение уже работало до того, как вы пришли с ИИ-агентом. Создать заново подсистему даже на 5000 строк для ИИ сложнее, чем фиксить баги и дорабатывать уже работающую систему на 2 миллиона строк.

## Мораль

- Самое серьёзное: сценарий фикса багов с агентами в крупном legacy-коде с отдельной Markdown-документацией у разработчика легко может сформировать грандиозную «ошибку выжившего», где он решит, что этого достаточно и для разработки с нуля — а тут различие как между дельтапланом и Шаттлом по сложности техник управления агентами.
- Сам по себе размер кода вообще не критерий сложности для ИИ, важнее его структура и логирование ошибок.
- Никакой проблемы навигации по крупному коду у ИИ нет, ему что-то особенное не требуется, если есть хотя бы нормальный лог, как в Comfy.
- Для агентов администрирования систем критически важно иметь доступ к их исходному коду для понимания логики их работы.
- Агенты администрирования систем довольно безопасно и точно могут накатывать хотфиксы на крупный код, пока разработчики ещё чешутся.

## Практический вывод

- Не бойся крупных кодовых баз — гоняй ad-hoc скрипты над корпусом (Think-in-Code), а не тащи всё в контекст; MCP/графы для навигации не обязательны при нормальном логе.
- Админ/терминальным агентам давай READ-доступ к исходникам обслуживаемой системы — black-box админить труднее, чем чинить с видимым кодом.
- Fix-legacy ≠ greenfield: успех правок на MD-доках не переносится на разработку с нуля («ошибка выжившего»).
- Паттерн «основная модель делает + субагент другого вендора консультирует на сложном» = cross-vendor верификация (см. навык the-algorithm).
